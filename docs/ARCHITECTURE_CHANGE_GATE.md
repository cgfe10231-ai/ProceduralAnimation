# ARCHITECTURE_CHANGE_GATE — 永久架构变更门禁

本文件只负责跨模块架构冻结和准入审核。禁止记录具体模块的修复过程、节点进度、Git SHA、测试成绩、特定场景参数或为单一模块开后门。所有任务与执行工具均受相同约束。

## 一、不可突破的架构底线
1. 判断以真实源码、存在的符号、可复现测试和实际产物为准，禁止把提案、测试脚手架或独立算例冒充生产实现。
2. 生产动作只能沿唯一运动规划—目标桥接—全身协调—Rig 解算链执行，禁止并行姿态写入和孤立控制器。
3. 每一层有唯一职责及独占的状态写权限；任何跨层写入或职责迁移均须正式批准。
4. 不可达、ROM 冲突、碰撞、身份损坏、未能证明恢复等失败必须如实呈现，不得静默吞没或虚报成功。
5. 已有能力优先复用；新模块必须说明不可替代性和与现有调用链的关系，绝不能为过某项测试临时复制控制流程。
6. 只读遥测不等于真实动力学反馈；接触几何不得通过硬编码平地、假力矩、假箭头或孤立演示场景替代。
7. 历史成熟动作、物理阈值、测试语义和唯一基准场景不得为局部修复被无关改变。

## 二、架构变更前后统一核查
1. 核对当前分支、HEAD、工作树、全局规则与最新状态文件。
2. 阅读真实源码与调用依赖，验证文件、类和接口物理存在。
3. 搜索现有实现，证明没有同职责模块或第二条控制链。
4. 明确新功能属于哪一层，调用方向是什么。
5. 明确输入输出、坐标空间、单位与数值边界。
6. 明确状态所有权、资源身份及事务责任。
7. 明确异常传播与失败恢复的唯一权威主体。
8. 明确对历史成熟动作、资产和测试基准的影响。
9. 冻结具体可写文件/函数、是否新增函数/模块及专项测试。
10. 任何架构变更先由负责人批准；任务完成后重新核查上述条件，不能事后追认。

## 三、审批与否决
- 发现必须变更架构时，停止修改、保留现场，由 ChatGPT 提交代码证据、必要性、风险、回归计划及明确授权边界。
- 项目负责人独占架构变更和主干合并批准权；Antigravity 不得自行解释批准或新设权限。
- 如发现越界、不同文档状态冲突、符号不存在、复现失败，必须立即停止，不得以“先修完”为由绕过。

## 四、验收
- 必须凭真实退出码、原始日志及实际场景证据判断；自动通过不能冒充人工视口验收。
- 禁止通过修改测试断言、跳过失败用例、静默误差截断或虚假数据取得验收。

## 五、文档治理
- **Antigravity 对全部 .md 默认只读；只有项目负责人主动明确授权文件范围、且 ChatGPT 已审定具体内容时，才允许逐字执行对应 Markdown 修改及 Git 收尾；禁止自主生成、修改或扩大范围。**
- 第一梯队只锁定长期规则；不可写单个模块的特例、任务结果、临时后门或当前进度。
- 规范变更须由 ChatGPT 独立审计、项目负责人明确批准；Antigravity 不得自主生成、设计或改写规范，仅可在负责人明确授权时机械搬运已审定的确定内容。
- 当前状态由 PROJECT_STATE.md、ARCHITECTURE_SYNC.md 与 docs/audit/production_interface/OPEN_FINDINGS.md 共同核实。交接摘要与历史报告不能推翻它们。
- 历史报告不可被为迎合当前进度而改写。任何修订必须保留原始历史可追溯性，不能悄悄加入局部授权。
